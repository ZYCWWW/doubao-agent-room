## 二、视觉工作台：把桌面软件拖进舞台（`686f55a`）

### 2.1 先证可行性，再谈实现

三件事都在你这台机器上实测过：

| 要验证的 | 结果 |
|---|---|
| Win32 窗口用 `SetParent` 嵌进自绘窗口 | 成功，内容正常渲染 |
| Win11 版画图（UWP 打包应用）嵌入 | 成功，工具栏、画笔、画布都在 |
| 记事本按窗口截图（`PrintWindow`） | 成功，灰度 32–255 不是黑屏，**被遮挡也抓得到** |

现有代码做不到的原因很直接：`core/screen_capture.py` 是 `pyautogui.screenshot()` 截整屏，`browser_click` 是整屏 0~1000 相对坐标，`pyautogui.click()` 挪的是真实全局光标——**整套代码里没有"窗口句柄"这个概念**。

### 2.2 方案：独立原生窗口，不进 Streamlit

Streamlit 页面（浏览器）当不了窗口容器，所以工作台必须是独立原生窗口，与面板并列、由面板起停。这条定下来之后，后面所有问题都是窗口层的细节问题。

### 2.3 四个真问题（都不是"理论上"的，是实测撞上的）

| 问题 | 现象 | 根因与处置 |
|---|---|---|
| 拖动画不出线 | 画布里只有一个点 | `SetCursorPos` 只改光标位置、**不产生 pointer 消息**，UWP 只看到按下和抬起；改用 `mouse_event` 注入绝对移动 |
| 嵌入后 UWP 内容偏移 | 画图右侧留黑、左侧"文件"被切 | UWP 有最小尺寸，强改尺寸会重新排版；改为**保持软件自然尺寸，只挪位置** |
| 舞台黑屏 | 截图抓到了豆包窗口 | 屏幕抓图被遮挡就抓到遮挡物，这是硬伤；改成按舞台矩形同源取图 |
| 拖入误触发 | 在舞台里拖动，目标窗口被换掉 | 拖放检测把舞台内的拖动当成了"拖入"；加了"按下点是否在工作台外"的前置条件 |

### 2.4 顺手抓到的一个一直存在的 bug

跑回归时 `workspace_cfg()` 返回空字典。查下去是：`test_suite.py` 的 ACL 用例直接替换内存 cfg，而 `add_path_action` 内部会 `save()`——**每跑一次回归，真实的 `config/vision_acl.json` 就被测试临时目录覆盖一次**（白名单从 `tmp7oy` 变成 `tmph78`，`workspace` 段被抹掉）。

修法：回归不再改写真实配置，`load` 按默认深合并（`6d571e9`）；补回被抹掉的 `workspace` 段（`1227bf4`）；清掉白名单里的测试残留路径（`aec2b04`）。

清空后行为复验：ACL 开启、白名单为空、`default_deny=true` 时，`check_action_permit` 返回 `(False, '路径不在白名单：…')`。**空白名单意味着谁都不许**，模型读写文件、扫描文件夹都会被拒——不是坏了，是没放行，要在面板「🔐 视觉ACL」页逐层加。

## 四、自建计算器（`e45e042`）

系统自带计算器是 `ApplicationFrameHost` 托管的"寄宿"UWP，`SetParent` 必然被拒——这也是上一轮拖入失败的真正原因（检测没错，是最后一步被窗口拒绝）。

第一版用 tkinter 自建，**被跨进程 `SetParent` 之后进程直接退出**，舞台整块全黑。所以改成**原生 Win32 窗口 + GDI 双缓冲自绘**：

- `apps/calculator.py`，类名 `AgentCalcWnd`、标题「计算器·内置」，380×540 起，最小 320×460
- 显示区（历史行 + 按位数降级的主显示）+ 4×5 键盘（`C ← % ÷` / `7-9 ×` / `4-6 −` / `1-3 +` / `± 0 . =`）
- 命中与按下高亮走 `WM_LBUTTONDOWN/UP`，键盘走 `WM_CHAR`，百分号按 Windows 计算器语义（`200＋10% → 200＋20`、`200×10% → 200×0.1`）
- 求值走 `ast` 白名单，只放行数字、正负号、加减乘除

实测：嵌入成功（`cls=AgentCalcWnd`、进程存活、舞台亮度 11 → 17.3 且出现 255 白色文字），`/click` 千分制坐标点 `7 + 3 =` 得 10，历史行正确。

## 五、拖入判定改「按下时那个窗口」（`0cefc43` + `2f408a2`）

根因有两个，缺一个都修不好：

1. **判定查错了时间点**。原来在**松手时**按落点坐标查窗口。这台机器上豆包客户端铺满 2560×1440 且置顶，压着舞台，查到的就是那块遮挡物；而且被拖的窗口一直跟着光标走，**事后回查按下点坐标也早就不是它了**。改成在按下那一刻就把 `window_at_point` 的结果记进 `_press_hwnd`，松手时优先用它（要求：还活着、不是工作台自身、不是本进程、有标题），落点窗口只当兜底。
2. **注入脚本自己把窗口点没了**。按下点取 `rect[0]+170`，在画图（1056 宽）上是标题栏中部，在计算器（380 宽）上已贴近右侧三个按钮；150% DPI 下按钮区从 `x≈1973` 起，而 1970 正好压在「最小化」上——一按窗口就缩，紧接着拖的其实是底下的豆包客户端。按下点挪到 `rect[0]+40` 后一次成功。

另有一处行为改动：拖入失败不再弹模态框，只更新状态栏。**Tk 的 messagebox 会卡住主循环，而且没有 Win32 按钮 ID、程序化点不掉**（`0cefc43`）。

## 七、AD 画电路图（今天的正题）

> 这一节的全部结论都在 AD 24.10.1（绿色包）上当场验证过。**已证伪的写法不要再试。**

### 7.1 起点：先证伪「带不动」

任务开始时你说的判断是"应该带不动了"。实测结果相反：

- AD24 绿色包在 `<本机路径>`（整包 5.59 GB，`X2.EXE` 41 MB），`%APPDATA%\Altium\Altium Designer {…}` 11 月 1 日还在写，说明确实用过
- 启动正常：`24.10.1`，pid 12728，内存 1033 MB，自动恢复上次工程「供电系统.PrjPcb」
- **3070 跑 AD 不吃力**：AD 基本不吃显存，主要靠 CPU 和内存，和本地模型争抢的不是同一类资源

**真正行不通的是"把 AD 嵌进舞台"这条路线**，与显存无关：

| 事实 | 数值 |
|---|---|
| 主窗口 | `hwnd=9701440`，cls `TDocumentForm`（VCL 顶层窗口，`SetParent` 理论上可行） |
| 尺寸 | `(-7,-7,1714,920)` = 1721×927，**最大化** |
| 舞台 | 1294×879 —— 装不下，也不能缩放，只能裁掉右下 |
| 顶层窗口数 | **89 个**（`SCH Library`、`Properties`、`Messages`…） |

所以走的是**脚本 / 离线生成**，不是视觉操作。顺带一条：千分制坐标在 1294px 舞台上 1 单位 ≈ 1.3px，原理图电阻偏 10px 网表就错脚——这条路本来也画不了电路。

### 7.2 脚本阶段拿到的事实

坐标单位是第一个坑，反复踩了很久：

**`Point(x,y)` 的参数单位是 1/100000 mil，所以 1 mil = `Point(100000, 100000)`。**

早期 `Point(100,100)` 只有 0.01 英寸，对象全部挤在原点 0.5 mil 内，看起来就是"加了却看不见"。判据是 `Location.X_Frac=50000`——小数部分而不是整数，说明坐标压根没落到格点上。

其余可用事实：

- 正确调用是 `SchServer.SchObjectFactory(eRectangle, eCreate_Default)`，**`SchObjectFactory` 是带参数的函数不是对象**；注册对象用 `SchServer.AddSchObject`，参数要带 Owner 文档
- `eLine` / `eRectangle` / `ePort` 三类图元都能创建，落盘坐标逐条对；
- `eLine` 写进文件的记录是 `RECORD=13`、矩形 `RECORD=14`、端口 `RECORD=18`
- **`OwnerIndex` 不是渲染的必要条件**——Port 同样没有 `OwnerIndex` 却能正常显示

操作层面的两个坑，已固化成流程：

1. **编译错误会留下执行锁**，下次运行直接 `Another script executing now`。必须先让脚本编辑器活动再 `Ctrl+F3`（Stop），只关错误框无效。**每次运行前先 `Ctrl+F3`。**
2. File 菜单展开后键盘会被图纸截走。`Alt+F` 之后要先按一次 `Down` 让菜单接管键盘，再用 `End`/`Up`×N/`Enter` 定位；而且**菜单项数量会随文档类型变化**（Schematic 活动时多出 Import/Export 子菜单），按固定次数 Up 必然点偏。

### 7.3 为什么脚本画不出线：5 组实验

| 脚本 | 写法 | 结果 |
|---|---|---|
| v27 | `eLine` + `LineStyle := eLineStyleSolid` | 日志 `line + LineStyle ok` / `done`，**线条不显示** |
| v29 | `eLine` + `eCreate_GlobalCopy` + `Color := 0` | 日志 `line globalcopy ok`，**仍不显示** |
| v30 | `W: ISch_BasicPolyline` + `W.Vertices.Add(...)` | 编译错 `Undeclared identifier: Vertices` |
| v31 | `ePolygon` + `ISch_Polygon` + `P.Vertices.Add(...)` | 编译错 `Undeclared identifier: Vertices` |
| v32 | `eWire` + `W.AddVertex(...)` | 编译错 `Undeclared identifier: AddVertex` |

加上此前的 `ISch_Wire.Corner` → `Corner` 也未声明。结论：

**`ISch_Wire` 在 DelphiScript 里只暴露 `Location` 一个字，端点集合在整条继承链上都不存在。**

官方接口继承链是 `ISch_Polygon → ISch_BasicPolyline → ISch_Polyline/ISch_Bezier/ISch_Wire`，但把变量声明成 `ISch_BasicPolyline` 或 `ISch_Polygon` 也不能让 `Vertices` 出现——这个名字本身就是未声明的。

**为什么 Line 不显示**：官方正常 SchDoc 里 6 条 Line 全部带 `OWNERINDEX` + `OWNERPARTID=1`，即真实"线"多是**元件符号内部图形**，不是图纸自由图元。这条不能完全闭环（Port 也没 OwnerIndex 却显示），但 `eLine` 作为"图纸自由图元"的身份确实可疑。

**取证过程中确认的两件反常事**：

- GUI 手画的紫线在屏幕可见，却**从未写进磁盘**，也不在 History 的 13 个快照里——它只存在于该 AD 会话内存
- `Ctrl+S` 与菜单 Save 都观测到不生效（mtime 恒为 `09:47:58`）

### 7.4 方案 2：Python 离线生成 ASCII SchDoc（**打通**）

路线判定过程，每一步都是实测：

| 尝试 | 结果 |
|---|---|
| 导出 `FileHeader` 裸记录流（`[4字节长度][\|RECORD=…][NUL]`） | AD 能打开、A4 图框正常，**图元全空白**，只读到图纸设置 |
| 三个流（`FileHeader`+`Additional`）拼接成完整文件 | 仍空白 |
| **官方样例**的裸流（2012 条记录、8 元件、280 引脚、6 条 Line） | **同样全空白** → AD 只是容错打开，并不真正加载内容 |
| AD 自己「另存为 → Advanced Schematic ascii (`*.SchDoc`)」 | **拿到权威格式**，纯文本可用 |

ASCII 格式就是纯文本：

- **latin-1 编码、无 BOM、首字节 `|`**
- 记录之间 **CRLF** 分隔，文件以 CRLF 结尾，没有空行
- 首行 `|HEADER=Protel for Windows - Schematic Capture Ascii…`

**决定性的那条规则**：

> **新增图元记录必须插在 `|RECORD=31|`（图纸配置）之后、任何 `|RECORD=6|` 之前。追加在 `RECORD=6` 之后的记录会被 AD 静默丢弃。**

之前所有"自造 Wire 不渲染"的尝试，失败原因只有这一个。定位过程：只改 `RECORD=6` 的 X2 → 紫线真的变长（ASCII 编辑生效）；追加 1 条 Wire → 不显示；照搬官方有效 Wire 记录（含 `INDEXINSHEET`）只换坐标并**挪到 RECORD=6 之前** → 曲线出现；五类图元随即全部渲染。

另外一个格式事实：**`RECORD=27` 才是真正的 Wire（导线）**，用 `X1/Y1/X2/Y2` 两点表达，和 Line 的 `LOCATION/CORNER` 不是一回事。官方样例里 `RECORD=27` 有 260 条。

产物两个：

- `gen_schdoc.py` —— `SchDoc` 类，`wire / rect / line / port / text / net_label` 六个方法，直接给坐标就能画
- `schdoc_template.txt` —— 从 AD 另存 ASCII 得到的模板记录（HEADER + 图纸配置 + 图纸参数）

### 7.5 从「方块」到「R1 / 10k」：真元件

只有矩形和导线不算电路图。真元件是这几类记录的组合：

| 记录 | 作用 |
|---|---|
| `RECORD=1` | 元件本体（Component） |
| `RECORD=2` | 引脚（Pin） |
| `RECORD=13` | 元件符号内部线 |
| `RECORD=34` | Designator（`R1`） |
| `RECORD=41` | Comment / 参数（`10k`） |

三条关键事实：

1. **`OWNERINDEX` = 父记录行号 - 2**（三个要素一致地验证过）
2. **`COLOR` 是 BGR 编码**：`16711680` 显示成蓝色，`255` 显示成红色
3. **`OWNERPARTID` 与 `ISHIDDEN` 的字段顺序不能动**——`ISHIDDEN` 被插到字段中间会破坏顺序

以及今天最隐蔽的一个 bug：

> 我用 `%` 格式化拼记录，串里的 `%%COMP%%` 输出后变成 `%COMP%`，而后面 `replace("%%COMP%%", …)` 找的是没被格式化过的原文，**替换永远不命中**。
> 结果是每个子记录的 `OWNERINDEX` 都写成了非法字面量 `%COMP%`：元件本体四条线因为 AD 容错还能画出来，但 Designator 和 Comment 挂不上父元件，**标签就整体消失**。

改成不含 `%` 的标记（`#C#` / `#P#`）后一次通过，`R1 / 10k / R2 / 10k` 全部显示。这条记进经验库了——`%` 和模板占位符不能混用。

### 7.6 PCB（`divider_pcb.PcbDoc`）

做法和原理图同构：让 AD 把官方板图另存成 ASCII，拿到格式约定，再用 Python 按记录拼图元。

- **PcbDoc 的记录名是字符串**（`RECORD=Board`），不是 SchDoc 的数字编号
- 需要的样本类型：Track / Pad / Via / Text / Component / Net / Arc
- 板框是 **5 个顶点**构成的矩形（`(1000,1000)-(5842.5,5650)`），可改
- **图元记录排在最后**

交付：86.4×50.8 mm 的板，7 个焊盘、4 条 25mil 顶层走线、5 条丝印文字（`GND/VIN/R1/R2/VOUT`），拓扑 `VIN — R1 — 中点 — R2 — GND`，VOUT 从中点向上引出。在 AD 24.10.1 里打开，焊盘（`RECTANGULAR` 生效）、走线、黄色丝印全部正确渲染。

`gen_pcbdoc.py` 是生成器，格式约定写在 docstring 里，改参数就能换板框、焊盘位置和文字。
