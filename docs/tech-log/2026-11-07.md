### 3.2 三个真 bug（提交 `37d5a73`）

1. **轮次耗尽把 Action 当答案**：撞 `max_round` 时 `last_output` 含 `Action:` 也被原样返回。改为返回 `[未完成] … 最后观测：…`。

3. **Action 解析失败只回裸错误**：模型不知道 JSON 错在哪，原样重试。补格式指引。

另删 `_build_context`（兼容壳，仅 1 个测试引用，与 `_context_head`/`_history_messages`/`_context_tail` 是同一件事的第二处实现）。

### 3.3 求证模式原本永远进不去（提交 `b51528f`）

`core/mode/strategy.py` 的 `predict_mode` 只看历史样本比例，样本 <3 一律 `steady`——新环境样本为 0，所以「求证：…」这类任务一律被当成工作模式。

改法：`predict_mode` 先查 `keyword_hint`，命中直接返回；未命中再走样本投票。3 行改动。

实测：

- 「帮我研究一下这个问题，我想探索几个假设」→ **inquiry**（原 steady）

## 六、知识注入加权（第二轮追加，提交 `828c6ee`）

用户原话：「结论回写是有必要的，他让模型专注于一个问题，至于不让他重复，可以外部注入其他话题来引导并给结论和新话题一个权重，谁权重大，谁注入的优势越大。」

核实后：**结论回写已经在跑**——`core/idle_scheduler.py:251-272` 有一段 R8 修复，求证收敛（成立/证伪）时写 `## 结论` 段、沉淀 `knowledge_fact`（`source=hypothesis_verified`）、已验证的再入 core 形态记忆。所以"专注于一个问题"的载体是现成的。

缺的是**注入排序**。改前的 `agent_chat._knowledge_inject` 只按向量距离取前 3 条，没有任何来源权重。后果可复现：某本书的条目距离一直最近，就永远占满 3 个名额，新结论挤不进来——这是小深连续 9 条咀嚼同一本书的机制性原因，不是模型爱复读。

改法（一处实现、两处共用）：`KnowledgeService.ranked_search()` 按 `effective = distance * weight` 排序。

| 来源 | 权重 |
|---|---|
| `hypothesis_verified` 求证结论 | 0.55（优势最大） |
| `conflict_resolved` 仲裁采纳 | 0.75 |
| 其余（书 / 用户投喂 / 工作结论） | 1.0 |

外加多样性兜底：前 top_k 全同源时，末位换成异源最佳项——这就是「外部注入其他话题来引导」。

两处调用方各自决定排除谁：chat 排除 `react_final`（闲聊不掺工作噪音）且给 `weight<0.7` 的条目**强提示**；main 首轮召回不排除（工作结论在主循环是有效参考）。

实测：结论 `dist=0.84` 经 `w=0.55` 得 rank=0.462，反超 `dist=0.60` 的普通知识排第一；三同源时末位自动换异源。168 测试全过、24.9 秒。

## 七、注入权重加入热度 + 冷门保底（提交 `c3deded`）

用户原话：「来源的权重还可以是回答的热度，但要加一条意识层面的引导，就是让他们意识到热度低点的不一定没有重要的意义，很多新突破都在冷门上。」

这句本身是完整设计：**热度要进权重，但不能只有热度**。热度是正反馈（被注入→记一次→更容易再被注入），没有对冲会把冷门饿死。

先测了写库成本才动手：`update_document` ~20ms（19.2 / 21.8 / 22.8），相对一次 LLM 调用（5–30 秒）可忽略，所以热度同步写回。

三个部件：① `heat_factor = 1/(1+min(heat,40)*0.05)` 封顶防热者恒热；② `cold_reserve=True` 时 top_k 内无冷门就把末位让给冷门；③ 冷门条目单独成段，段标题即「热度低不等于不重要，很多突破恰恰出在冷门方向」。

保底只在闲聊开——主循环没有引导语配套，硬塞一条冷门只会挤掉相关内容。

实测：同距离下 heat40→0.20 / heat10→0.40 / heat0→0.60；不开保底时冷门(0.70)被热门(0.24/0.30)彻底挤出，开保底后末位换成冷门；`bump_heat` 写入回读 2→3。

**一个探针坑**：第一次用 `coll.query(top_k=3)` 回读刚写的条目，没命中就返回 `null`，差点误判成"heat 存不住"。必须用 `coll.get(ids=[doc_id])` 精确回读。

**一个测试坑**：`test_suite.py` 会重定向 `CHAT_ROOT`，状态文件若写成模块常量就会写进真实目录。改为函数内从 `CHAT_ROOT` 派生。

168 测试全过、23.5 秒。

## 十、身份即「他自己」（`e8676b6`）

用户提了一个目标机制：每个人做事都有目标，分三层——潜意识目标（自己不说、甚至不知道，表现为症状而不是诉求，比如「太累了」实际是「想找个舒服地方」）、意识目标（能说清的，比如「找家好吃的餐厅」）、身份目标（角色给定的优先级：上班=把事做好、学生=好好学习、他自己=兴趣和生活）。热度是「多数人的目标在这个事物上聚集」，冷门是「少人做但做的人各有动机」。

用户对上一版 `_identity_system` 的两次纠正：

1. 「聊天的时候他们的身份应该是他们自己」——我原来写的「你擅长：推理 逻辑 论证」是岗位说明书，是工作身份，不是他自己；
2. 「不仅仅是兴趣、生活，是不限制，想什么都行，但要有思维逻辑。口头禅删掉，不需要的。」

**改动里最有价值的一件事，是找到了空转的真因**：不是「擅长不匹配」，而是 system 里硬写了 `口头禅：哎呀，好可爱！`。小深每轮以它开场、Qwen 以「嘿嘿嘿」开场，都是这句在诱导复述。删掉整行（连同 `catch` 变量）之后，同类话题下小深输出的是「章鱼的心脏专门泵血到触手，这也是它们能在水里自由游动的关键……触手既捕猎也导航……皮肤感觉器感知环境」，有因果有递进；Qwen 接住「蓝色血液」并补了血蓝蛋白含铜，再自然延伸到蛇。改动前它们只会输出零信息套话。

三处改动（全在 `agent_chat.py` 原地，可整块删）：

| 位置 | 改动 |
|---|---|
| `_identity_system` | 删 `口头禅：X` 整行；身份段改成一句通用话——「你是你自己，不是工具。想什么方向都可以，不限于兴趣或生活；但说话要讲逻辑——有判断就给理由，没想清楚就说没想清楚，别用空泛的感叹句凑数」 |
| 新增 `STRENGTHS` + `_fit_score` | 只用于「谁先开口」的调度，不写进 system、不限定他们想什么；全 0 命中退化为纯随机 |
| `_chat_round_impl` 低负载分支 | `random.shuffle` → 按相关度排序（同分随机），保留原有 `speak_p` 意愿 |

顺手修了 `intro` 自带句号导致的「性格：……。。」双句号。

**三个踩过的坑**：

1. 第一版拿小深的实际毛病当例子写进所有模型的 system：`别拿「好可爱」「真有趣」这种套话凑数`。对没说过这话的 Llama、Qwen 是噪音，甚至可能反向诱导——给模型一个它本来不会用的词，等于提示它。改成概括说法「别用空泛的感叹句凑数」。
2. 「不擅长可以沉默」也是错的。聊天里朋友不会因为不懂就不开口；而且这条会把沉默合理化，正是空转的另一种形态。删掉，改成「跟话题不沾边就照实说此刻的第一反应」。
3. 验证方式：走 `chat_round` 连续两次都只出一个模型，误以为 Qwen 输出为空。实际是长聊/测试同时占着 Ollama，请求排队超时，`_ask` 里返回 None 静默跳过、也不打日志。最后改成**单模型直问**（自己拼 system + user 直接调 `ask`）才拿到干净结果。这台机器 <本机配置> 跑三个本地模型，任何两个 LLM 任务并行都会互相拖慢——验证必须串行。

房子图是 networkx 的 house graph，颜色、节点数、边数、拓扑全部说对。**之前那次超时不是模型不行，是长聊抢了 Ollama。**

### 11.3 三处改动

设计口径：**只认显式工具语法，不做自然语言触发**。依据是读书工具的前车之鉴——`_maybe_exec_book` 挂在每次发言后靠模型自发，`chat.md` 全文 0 次 📖 成功广播，一次没真触发过。但视觉比读书更重（一次 30–80 秒，比一轮闲聊还长），若连"我看看这图"这种自然语言都放行，一个 4B 模型随口一句就能把整条接龙卡住一分多钟。

| 位置 | 改动 |
|---|---|
| `_SYS`（`agent_chat.py:187`） | 加视觉用法说明（只覆盖 chat 模式） |
| 新增 `_maybe_exec_vision`（`_maybe_exec_book` 之后） | 正则抓 `vl_analyze_image("路径", "问题")` → 执行 → 广播 `📷` |
| 挂载点 `:720` | `_maybe_exec_book` 之后加一行 `_maybe_exec_vision` |
| `long_chat.py:435` | 广播跳过列表加 `📷`，否则看图结果会被当成新发言再触发接龙 |

`_maybe_exec_vision` 的三个设计点：路径上限 260 字符、问句可选上限 120；`_last_vision_ts` 懒初始化（60 秒冷却，防连环触发）；失败**不做静默**——与读书的自然语言分支相反，因为它需要知道"没看到"，否则会硬编图里的内容。

### 11.4 两轮真问题（第二版才打通）

第一版提示词写完就测，**三个模型全都不输出语法**（单模型直问，自己拼 system + user 直调 `ask` 才拿到干净结果）：

- `deepseekR1Q7B`：「我是 AI，无法直接查看图片，建议你复制到图片编辑器里看」——它的自我认知是对的（它确实无 vision），但不知道可以走工具；
- `llama3.1:8b`：「我会尝试调用视觉模型，观察这张图」——知道有这能力，但没写语法；
- `qwen3.5:4b`：「我先调用视觉模型仔细瞧瞧细节」——同上。

问题出在措辞是**背景介绍**，不是**动作指令**。改成「你自己看不了图片，但可以让老师替你看。想看某张图，就在发言里原样写这一行：`vl_analyze_image(...)`……没看到图之前不要猜图里画了什么」之后复测，Qwen 一次就吐出了完整调用：

```
vl_analyze_image("<本机路径> "这张图的细节内容是什么")
```

这暴露了第二个问题：**模型会自己改写路径格式**，写成双反斜杠 `<本机路径>`，个别还会带 `file:///` 前缀。在钩子里统一归一化（`\\`→`\`，剥 file 前缀）后再交给视觉工具。

第三个问题是超时：`vl_vision_tool` 复用 `ollama.timeout = 120`，而单张实测就要 76.9 秒，稍有资源占用就爆（实测 122.1 秒直接失败）。新增 `ollama.vision_timeout = 300`，只在视觉链路生效，其他请求仍 120。

### 11.5 验证结果

- 直调 `vl_analyze_image`：空白图 33.9s、房子图 76.9s，内容全对；
- 走 `_maybe_exec_vision` 端到端：62.7s、无异常、`chat.md` 360→367、广播出 `📷 【小深】想看 …` 与完整识别正文；
- 用 Qwen 真实输出喂钩子（含双反斜杠）：65.6s 成功，路径归一化后正常打开；
- 长聊 16:09 重启后正常出 🎯 话题，三个模型接龙无异常。

**一个诚实结论**：三个模型里目前只有 Qwen 会自发写出这个语法，Llama 仍只说"想看看"、DeepSeek 完全不提。这和读书工具是同一个概率问题——工具能力接进去了，会不会用取决于模型。若要稳定触发，得走服务端驱动（由豆包在检测到图相关话题时主动调用），那是另一件事。

### 11.6 后续补全（`4ab3539` + `d84c7f4`）

**求证/工作模式补上视觉说明**。原来只有 chat 模式知道能看图，而求证时拿图表、截图、手稿当证据恰恰最需要。三个模式现在都有，`_SYS_GAME` 没加（游戏用不上）。校验：`mode_sys` 对 chat/proof/work 均含 `vl_analyze_image`，`{task}` 占位符正确注入、无残留。

**视觉调用前先查路径真伪**。模型很容易编一个像样的路径（尤其被要求"看看某张图"却没给真实路径时），而白跑一次视觉要 30~80 秒。现在 `_maybe_exec_vision` 在调用前 `os.path.isfile` 检查，不存在就直接广播「这个路径不存在，我没看到图。请确认路径写对了再说，别自己猜图里的内容」。

实测：假路径、相对路径均 **0.02 秒**返回并如实广播，而原来要空耗一分钟。

**关于 ACL 的处理决定（有意不加）**：`vision_acl` 白名单当前只有 `<本机路径>`，且 `default_deny: true`。如果把 `vl_analyze_image` 也接到 ACL 上，视觉就只能看那个临时目录——刚接通的能力立刻废掉。所以这里选择**保持现状 + 记录风险**，而不是为了合规把功能锁死。要收紧的话，正确做法是给视觉配一个独立的图片根目录白名单（比如 `<本机路径>`），而不是复用 scan_folder 那套。

### 11.7 长聊重启后空转：`337a631` 只修了一半（`49ff03a`）

改完视觉代码后重启长聊验证，发现一个更麻烦的现象：`chat.md` 停在 382 行、日志停在「向量库预热完成」之后，**2 分半钟没有任何接龙，一条 LLM 请求都没发**。

排查结论：`run_forever` 是**事件驱动**的，主循环第一句就是 `_wait_chat_event()` 阻塞等目录写入事件。而 `start_service()` 里的 `📡 闲聊继续` 播报是在**进入这个循环之前**写的——那次事件已经被错过，之后没有新写入，循环就永远等不到，进程活着但完全空转。

**为什么上次没暴露**：15:51 那次重启，最后一条真实对话距离当时 > 600 秒，走的是 `_open_topic()` 分支，开话题本身产生了一次写入，正好把循环唤醒。这次距离只有 5 分钟，走不进那个分支，就卡死了。

所以 `337a631` 和 `49ff03a` 合起来才是完整修复：

| 启动时最后一条真实对话距今 | 旧行为 | 现行为 |
|---|---|---|
| > 600 秒 | `_open_topic()` 开新话题（正常） | 不变 |
| ≤ 600 秒 | **什么都不做 → 永久空转** | `chat_round(mode="chat")` 主动接一轮 |

验证：重启后日志出现 `[long_chat] 回应 2 条`，`chat.md` 382→388，小深和 Qwen 顺着前面达·芬奇 / 郑和的话题继续接龙。

**教训**：事件驱动的常驻服务，启动时自己写的那条「启动播报」不构成有效唤醒信号——它写在监听开始之前。凡是"等别人写文件才动"的循环，都得在进入循环前自己先踢一脚，否则第一次唤醒就要靠外部运气。

### 11.8 让它们自己调用：上一轮的结论是错的（`a4807df`）

用户问「能让它们自己调用吗」。做了一轮对照实验后，发现**前一轮"只有 Qwen 会写、Llama/DeepSeek 不会"这个结论是错的**，两个"不会"各有各的真原因，而且都不是能力问题。

**实验方法**：同一张真实存在的 house graph 图、同一句提问（「我自己看不了图，但想知道它画的是什么，你打算怎么办」），只换提示词策略，直问 Llama 8B 与 DeepSeek R1 7B。

| 策略 | Llama 8B | DeepSeek 7B |
|---|---|---|
| A 现状（原 system 措辞） | **其实写了，但被包在引号里** | 说「可以使用 VLANalyzeImage 工具」，不写语法 |
| B 给完整示例 | 写出（29.8s） | 说「想让老师替我看」，并**开始猜内容**（猜成"深蓝色的房子"） |
| C 禁止空话 | 写出（7.5s） | 只回一句「我想知道图片画了什么」 |
| D 先自检 | 写出（7.6s） | **写出**（41.8s） |
| E 先自检 + 禁编造 | 写出（54.9s） | **写出**（352.6s，含一次超时重试） |

**两个真因**：

1. **Llama 一直都会写，是我的正则没接住。** 它在"现状"版里输出的是 `<本机路径>` —— 整行被包在一对双引号里、内部引号还带 `\"` 转义。而钩子正则要求 `(` 后紧跟引号，遇到反斜杠就失配，于是被判成"不会用"。**这个引号是我造成的**：system 里写成「原样写这一行：\`vl_analyze_image(...)\`」，用反引号包裹，模型理解成"要带引号"。

2. **DeepSeek 不是不会调用，是直接编。** 它 154 秒后输出「图片展示了一个用 3D 建模软件制作的现代建筑结构示意图，展示了框架、屋顶、窗户和门框」——而实际那张图是 5 节点 6 条边的图论示意图。它根本没有调用，就给出了一段听起来很专业的描述。

**三条修改**：

| 位置 | 改动 |
|---|---|
| 三个模式的 system | 去掉反引号包裹；改成「你先自检：你知道那张图画了什么吗？不知道。不知道就别猜，把下面这一行直接写进发言」 |
| 三个模式的 system | 加禁编造硬约束：「你绝对不能凭空描述图里有什么。"图片展示了…""图上画着…"只有在你刚看到 📷 开头的识别结果之后才能写」 |
| `_maybe_exec_vision` 正则 | 引号前允许一个可选反斜杠 `\\?`，兼容 `"` 与 `\"` 两种写法 |

**验证**：

- 正则三形态全过：普通、`\"` 转义包裹、反引号包裹，都能抓到
- 三个模式 system：chat 629 字 / proof 399 / work 267，均含视觉说明与禁编造约束，无 `{task}` 残留、无反引号
- 实测 Llama 写出 `<本机路径>`、DeepSeek 写出 `<本机路径>`，**都是真实路径、单反斜杠、格式规范**
- 端到端把 DeepSeek 的真实输出喂给钩子：正则可命中，广播出 `<本机路径>`，路径归一化生效（视觉本身因长聊抢资源超时 300 秒，属已知现象）

**结论**：三个模型现在都能自己写出调用。关键不在"教它这是你的能力"，而在**先把它逼到"我不知道"这个事实面前**——没有退路，它就只能要么调用、要么承认不知道；再补一条"不许编"的硬约束，把"承认不知道"之外的路也堵上。

### 11.9 视觉调用改后台执行：不再为一张图停住整轮（`0bc2be2`）

11.8 解决了"它们会不会写"，但这个写法本身还有个要命的前提：**写出来之后是要同步执行的**。`_maybe_exec_vision` 直接调 `vl_analyze_image`，而这个调用最长 300 秒。DeepSeek R1 自己发言就要 350 秒，再叠一次视觉，一轮能拖到十分钟——接龙等着，谁也没话说。

改法是把执行和解析拆开：

| 阶段 | 原来（同步） | 现在（异步） |
|---|---|---|
| 解析 + 冷却 + 路径预检 | 同步 | 同步（都是微秒级） |
| 通报"想看这张图" | 无 | 立即广播 |
| 真正调视觉 | 同步，卡住整轮 60~300 秒 | 丢进后台线程 |
| 结果回群 | 同一次调用内广播 | 线程完成后单独广播 |
| 接龙 | 等视觉跑完 | 立刻继续 |

配套三个约束：
- `_vision_busy` 互斥：同一时刻只跑一个视觉任务（<本机配置> 机器并行会互相拖慢 Ollama）
- 60 秒冷却保留，防连续触发
- 路径预检仍在同步路径里，假路径 0.02 秒返回

**关键前提是确认了长聊不会因为这条广播而卡住**：`long_chat.py:471` 的跳过列表里本来就有 `📷`，豆包发出的看图结果不触发接话——这条原本是为了"别让豆包结果自动带起一轮"，现在正好让异步结果落地不打扰接龙节奏。

而结果不会白丢：`_recent()` 只过滤 `豆包：[📡🔕]`，`📷` 和 `📖` 是保留的。所以视觉结果写完 chat.md 之后，**下一轮任何人发言时都能从 `_recent` 读到**，形成「想看 → 看到 → 接着聊」的闭环，只是不再需要为等这张图停一整轮。

**验证**：真路径调用 **0.0 秒返回**（原来最多 300 秒），`_vision_busy` 置位；桩函数替掉视觉后，后台线程正确广播「看完了」、内容进群、`_vision_busy` 复位为 False；假路径 0.0 秒返回；冷却期内的重复调用被静默跳过且不写盘。

**顺带澄清一个误会**：中途发现 chat.md 从 406 行掉到 202 行，一度以为清理脚本删错了。查下来是长聊的摘要滚动在 17:11 触发，裁掉的 209 行**完整归档**到 `archive\chat-20261107-171127.md`，且无任何测试残留——数据没丢，本来就是要"保存聊天记录"。

### 11.10 接龙超时 90 秒是真凶：慢模型会整轮缺席（`dfd5391`）

11.9 之后我以为视觉不再拖累接龙就万事大吉了。用户说「就这样吧，慢点就慢点，大家都能发表看法」——这句话把验收标准点明了：不是快，是**每个人都能出声**。按这个标准回头查日志，发现原设计根本达不到。

**证据**：

- `long_chat.log` 里 30 条慢调用，**21 条超过 90 秒**，记录到的峰值 367.8 秒
- 22 条 `LLM请求失败`，其中多条明确写着 `read timeout=90.0`
- 失败时刻（15:18 / 15:25 / 15:57 / 16:56）与同秒的 `慢调用 277.7s` 一一对应

277.7 秒这个数字是关键线索：`llm_client.chat` 里 `max_attempts=3`，90 秒 × 3 次 + 退避 ≈ 277 秒。也就是说，90 秒超时后它还会重试两轮，**三轮回满才判定失败**，然后 `_ask` 返回 None，这个模型这一轮就彻底不出声了。

所以原设计的实际行为是：慢模型每次发言要陪跑 277 秒，最后还是失败、缺席。既慢又没发言——两头都亏。

**改法**：把接龙超时从 90/120 秒提到 **400 秒**。

| 位置 | 原来 | 现在 |
|---|---|---|
| `_ask` 默认值（高负载用） | 120 秒 | 400 秒 |
| 低负载接龙显式传参 | 90 秒 | 400 秒 |

400 这个数字是从实测峰值取的：历史最高 367.8 秒，留了约 30 秒余量。重试次数仍是 3 次，但单次窗口拉长后基本不会触发，容错还在。

**验证**：`timeout=90` 已全部清除（0 处残留），`timeout=400` 两处；`ask_default=400.0`；底层 `llm_client` 的 `timeout = timeout or self.timeout` 与 `llm_gateway` 的 `if timeout is None` 都确认"显式传参优先"，400 能真正传到 `requests`。

**取舍**：最坏情况（真卡死）一轮会等更久。但既然用户明确接受"慢点就慢点"，而缺席发言是不可接受的，这个方向是对的——慢是代价，缺席是失败。

## 十三、遗留

1. `add_reflection` 仍零调用（`reflection` 分区目前无人消费），未接。
2. 本地模型在聊天里显示英文 ID（如 `Llama`），因为角色库无此模型。用户此前已明确"去除桌面人物与形象"，故未补角色。
3. `main` 保持 R1，单任务 30–60 秒。若后续换卡或换模型，需要重跑 3.1 那组对比再决定。
4. 长聊服务尚未随面板自动开启；摘要/注入新逻辑目前只验证了手动触发与单轮链路。
5. **视觉自发触发率低**：三个模型里只有 Qwen 会主动写出 `vl_analyze_image(...)` 语法，Llama 只说"想看看"、DeepSeek 不提及。工具能力已接通，是否使用取决于模型自觉。若需稳定使用，得改成服务端驱动。
6. **视觉说明只覆盖 chat 模式**：`_SYS_PROOF`（求证）与 `_SYS_WORK`（工作）都没加，那两个模式里它们不知道能看图——求证时对照图表恰恰最有用。
7. **`vl_analyze_image` 不受 ACL 管控**：`vision_acl` 白名单只管 `scan_folder`，视觉工具本身直接读任意路径。**有意没加**——把视觉接到现有 ACL 上会让它只能看那个测试临时目录，等于废掉能力。要收紧得单独配图片根目录白名单（见 11.6）。
8. 长聊运行时做视觉会明显变慢（<本机配置> 机器上两个 LLM 任务抢资源），300 秒已留够余量，但体验上会感觉"卡了一会儿"，属预期行为。
