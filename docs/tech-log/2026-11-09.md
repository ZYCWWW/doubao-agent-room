## 四、查询切分的老 bug：正则把专有名词吃掉了

第 2/4 步构造 bing 查询时用的是：

```python
re.sub(r"[\u4e00-\u9fa5]{1,3}的", " ", t)   # 「水的沸点」→「 沸点」
```

「运算放大器的带宽与增益关系」被它处理成 **「运算 带宽 增益」**——因为「放大器的」正好匹配
`1~3字 + 的`，被当修饰语删了。bing 于是返回**位运算教程**。

**修法：切分而不是删除**——按 `的|与|和|及|标点` 切开，每段保留完整名词短语，只丢 1 字碎片：

```python
for p in re.split(r"的|与|和|及|、|，|,|。|；|;|：|:|—|-|\s+", t):
    k = p.strip()
    if len(k) >= 2 and k not in keys: keys.append(k)
```

修复后：`['运算放大器', '带宽', '增益']`、`['沸点', '海拔高度']`、`['开关电源', 'EMI抑制方法']`。
**这条比"删 X的"更根本——删修饰语会误伤长名词，切分才安全。**

## 九、扫描版书：从"抽不到就跳过"到"按需 OCR"

**用户原话**：「光学可以，高等代数是扫描版，我用 WPS 转换一下」

**实测推翻了前半句**（`<本机路径>` 里就 2 本，全都无文字层）：

| 文件 | 页数 | 文字层 |
|---|---|---|
| 光学（第五版）赫克特 | 871 | 每页 0 字 |
| 高等数学第六版（上册）同济 | 418 | 每页 61 字，且是水印 `/www.1zhao.org/viewthread.php?...` |
| 新概念物理教程-光学-赵凯华（G 盘） | 421 | best_page_chars = 0 |

**不建议 WPS 整本转**：871 页要几小时，而七步一次只需要 240 字。
改成 `core/external_kb.read()` 的按需 OCR 兜底：

- 装了 `rapidocr_onnxruntime 1.2.3`（连带 opencv-python 5.0.0.93 / Shapely / pyclipper / six）
- 文字层 < `MIN_TEXT`(120) 字 → 判定无效（水印页常见的 61 字正好被这一条挡掉）
- 抽样 OCR **第 8/18/40 页**（`OCR_OFFSETS`），取最长结果——从第 0 页起只会识别到扉页书名
- 结果落 `sandbox/chat_space/ocr_cache/<md5>.txt`，第二次同页 0.0s
- `read(..., ocr=True)` 可关闭；pipeline 只给前 2 本开 OCR（`ocr=(idx < 2)`），
  否则 4 本全扫描版要多等 1 分钟

**实测**：

| 书 | 方式 | 耗时 | 产出 |
|---|---|---|---|
| 赫克特光学 第 20 页 | OCR | 8.5s | 1189 字：惠更斯/牛顿/欧拉与消色差透镜 |
| 同济高等数学 第 30 页 | OCR | 5.2s | 659 字：数列极限的 ε-N 定义 |
| 赵凯华光学（采样偏移生效后） | OCR | 26.5s | 朗伯余弦定律原文 |
| Fundamentals of Power Electronics | 文字层 | 0.8s | 原路径不受影响 |

**已知误差**：`10⁸` 经常被识别成 `10%`，`α`/`a`、`ε`/`e` 会混。用于"定方向"够，
不能直接当引文数值。

## 十二、视觉工作台把桌面嵌走导致的黑屏事故

**现象**：凌晨跑完安全体检后，用户报「我屏幕黑了」。截图确认桌面全黑无图标、
任务栏可见；几分钟后任务栏也消失，全屏只剩一个悬浮头像。

**误判过程**：先怀疑显示器电源管理（`powercfg` 显示电池模式 3 分钟关屏），
但 `cu` 注入的鼠标移动唤不醒；再查显卡（<本机配置> + UHD 770 均 OK、无 4101
TDR 事件、explorer 自 11/4 稳定运行未崩），排除硬件。

**真正根因**：视觉工作台把系统外壳窗口当成普通软件嵌进了舞台。

1. `core/desktop/win32_api.py` 的 `list_windows()` 只过滤「无标题」窗口，
   而桌面窗口 `Progman` 的标题是 **"Program Manager"**，有标题、尺寸全屏，
   所以它会出现在「可嵌入窗口」列表里。
2. `services/vision_workspace.py` 的 `_attach_hwnd()` 调 `wa.attach()`，
   而 `attach()` **完全没有「不能嵌入系统窗口」的判断**。
3. 结果：`SetParent(Progman, 舞台)` + 改成 `WS_CHILD` → 桌面（壁纸+图标）
   整块搬到舞台里，屏幕原位变黑；任务栏在 `Shell_TrayWnd` 上，一并被夺后
   连任务栏也没了。
4. 致命一击：宿主销毁会连带销毁作为子窗口的 `Progman` / `Shell_TrayWnd`，
   **explorer 不会自动重建**，桌面就此消失，`FindWindowW("Progman")` 返回 0。

**修复**（`core/desktop/win32_api.py`）：

- 新增 `_SHELL_CLASSES`（progman / workerw / shell_traywnd /
  shell_secondarytraywnd / windowsdashboard / multitaskingviewframe /
  dv2controlhost）与 `is_shell_window()`（另含所有 `shell_` 前缀）
- `list_windows()` 枚举时跳过这些窗口，它们不再出现在「可嵌入」列表
- `attach()` 入口硬拒绝，返回「这是系统外壳窗口（桌面/任务栏），不能嵌入舞台」

三处入口（`/windows` 列表、`/attach` 按标题查找、`/poll_drop` 从桌面拖入）
全部被这层防护兜住。

**恢复手段**：先确认工作台已退出（端口文件消失），再
`Stop-Process -Name explorer -Force` 让系统重建 explorer。实测重启后
`FindWindowW(Progman)=132358`、`Shell_TrayWnd=131878`，壁纸与全部桌面图标回来。

**验证**：`is_shell_window(WorkerW) = True`；`list_windows()` 不再含
`progman` / `workerw` / `shell_*`；回归 `159/159 OK`（26.5s）。

**教训**：`SetParent` 能搬走的不只是应用窗口——凡是有标题、有尺寸的顶层窗口
都可能在列表里，系统外壳（桌面/任务栏/开始菜单）必须显式拉黑。

## 十三、功能插件化：科研七步作为范式（2026-11-09 凌晨）

## 16.4 这一轮修掉的六个实际问题

**① `tools/book_tool.py` 语法崩溃。**
上一轮给一批工具加迁移注释时，我把 docstring 的闭合三引号插进了中间，导致第 6 行 `- 文字版 PDF / txt：…` 裸在代码里（三引号提前闭合，后半段成了代码）。回归第一次跑直接 `SyntaxError: invalid character '：' (U+FF1A)`，159 里 1 个 ERROR。修法：注释挪到 docstring **闭合之后**、`import os` 之前。

**② 面板里塞 Windows 绝对路径会被吃掉。**
`st.markdown(f"**会话** `{sid}`　**沙盘根** `{SANDBOX_ROOT}`")` 在页面上显示成 `<本机路径>` —— 反引号被当代码块吃掉、反斜杠被当转义。先查证 `SANDBOX` 实际只有一个值（不是数据问题），才确认是渲染问题，改成 `st.write` + `st.caption`。

**③ `node_id` 渲染两遍。**
`st.caption(f"node_id: `{nd.get('node_id')}`")` 页面上出现 `node_id: 80317efc node_id: 80317efc`（放大截图逐字确认）。改纯文本 `st.caption("node_id: " + str(...))` 后恢复正常。

**④ 快照列表同样重复。**
`st.markdown(f"- `{sp.get('name')}`　{ts}")` 把快照名渲染两遍（两条一模一样的 bullet）。改成 `f"- **{name}** —— {ts}"`（加粗，不用反引号）后只剩一条。

> **这个 Streamlit 版本里「反引号 code-span + 中文或长十六进制串混排」会重复渲染内容**，本轮连踩三次（沙盘根路径、node_id、快照列表）。统一规避：面板文案用 `st.write` / `st.caption` 纯文本拼接或 `**加粗**`，不用反引号包变量。

**⑤ F5 后沙盘"看起来是空的"。**
Streamlit 每刷新一次就新开 session、`st.session_state.sid` 重新生成（本轮实测连续 F5 得到 `878687f0-…` → `0bc25097-…` → `4434fc24-…` → `3ff1db5b-…` → `c16c75df-…` → `ec0830b6-…`，每刷一次一个新目录），而历史草稿都挂在旧 sid 下。解法：加会话选择器 + `_all_sessions()`。

**⑥ 非会话目录混进下拉框。**
沙盘根下还有 `research` / `crew` / `chat_space` / `hypothesis` 四个业务目录，截图确认它们被列进了下拉框。加 `_SID_RE`（UUID 正则 `^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$`，`re.I`），同时过滤 `_all_sessions()` 与 `_latest_session()`，改后下拉框只剩 UUID 会话。

**⑦（补充）一进来就是空页。**
F5 生成的新会话沙盘必然为空，打开页面就是"这个会话的沙盘还是空的"。加 `_has_content(sid)`（有真文件或有节点即算有内容），当前会话为空时默认落到最近**有内容**的会话上；用户手动切过之后 `sp_sid` 记住选择，不再干扰。

### 17.1 快照 tab 点不开：是坐标，不是代码

上一段遗留的"浏览器里点 📸 快照 tab 一直点不中"，本轮定位到了真因。

- `y=850~852`（cnt 55/56/55）：**选中 tab 的红色下划线**

下划线在 **851 px**。而我之前一直按 cu y=728（= 786 px）点，**整整偏上 65 px**。

### 17.2 "重复渲染"的真因：不是反引号，是 inline 格式混排

快照 tab 点开后，列表仍然是两行：

```
• 20261109_030836_selfcheck —— 2026-11-09 03:08:36
  20261109_030836_selfcheck —— 2026-11-09 03:08:36
```

第一行有 bullet，第二行缩进对齐 —— 这是 markdown **列表项续行**的典型形态，不是两条数据。

先把数据侧查清水落石出：

- `imaginary_service.list_snapshots(sid)` 返回 `[{'name': '20261109_030836_selfcheck', 'created_ts': 1794164916.87}]`，**只有一条**
- 拼出来的字符串 `'- **20261109_030836_selfcheck** —— 2026-11-09 03:08:36'`，`repr` 里**没有换行**，长度 54

所以是渲染层把一个 list item 拆成了两行。上一段的"反引号 code-span"结论**只对了一半**：
真正触发条件是**同一行里出现多个 inline 格式片段**，反引号只是其中一种。本轮把 `**加粗**` 也去掉后
才彻底正常。

### 19.5 三个真实缺陷（全属 Streamlit 时序坑，可进经验库）

这一版初稿在浏览器上撞了三个坑，其中第三个排查了整整一轮，最后定性为渲染时序而非数据
丢失。

**缺陷一：按钮后置写入 vs 页面顶部提前取值。**
初版把 `sessions = debate_list()` 写在函数最前面。点「发起辩论」时，同一帧里这个
`sessions` 还是按钮执行前的旧值，于是出现「绿框已发起 + 下方仍显示共 0 场辩论」。
修法：顶部只留 `_has_any = bool(debate_list())` 决定 expander 默认展开态，真正的
`sessions = debate_list()` 挪到 expander 之后。

**缺陷二：`StreamlitAPIException` 被 registry 吞掉，整页下半部塌掉。**
初版提交成功后，在按钮分支里写 `st.session_state["dp_say"] = ""`。此时 widget 已实例化，
Streamlit 抛异常 → `registry.render_panel()` 的 try 捕获后 `root_logger.error` →
页面下半部渲染成「插件 debate_plugin 的面板渲染失败…」兜底块。**看起来像插件加载失败，
实际是页面代码 bug。** 修法：text_area key 改成 `dp_say_<seq>`，另加 `dp_say_seq` 递增，
下次 rerun 自然是一个全新的空框。

**缺陷三（本轮定性）：指标区滞后一帧，看起来像数据回滚。**
现象：提交插话后绿框显示「已记入第 1 轮」，但同一场再提交**还是第 1 轮**，指标区始终
`发言：0 条 共识分：0.000`。

排查链（全部是浏览器实测，不是推理）：
1. 加 DEBUG caption 打印 `debate_speak` 返回的 round + `get_session(s.id).turns` 长度 +
   是否同一对象 → `returned round=1 / live turns=1 / same_obj=True`。**写入完全成功。**
2. 保持页面不动，点侧边栏「🗣️ 辩论现场」触发一次纯 rerun → 指标区立刻变成
   `发言：1 条 共识分：0.400`。**数据一直都在，只是上一帧没渲染到。**
3. 再提交一次空内容，提示「发言内容不能为空」；滚回指标区仍是 1 条 —— 没把数据弄丢。

结论：**根因是渲染顺序**。信息区（发言 X 条 / 共识分）渲染在三个 tab 之前，而「提交这一轮」
按钮在 tab 内。Streamlit 一帧内从上往下执行，按钮写入发生在指标区已经画完之后，于是同一帧
指标区显示的是写入前的旧值，下一次任意 rerun 才更新。之前误判为「数据回滚」，是因为连续
两次提交看到的都是顶部那一份旧值。

修法三处：
- 顶部加一次性消息通道 `_msg = st.session_state.pop("dp_msg", None)` + `st.success(_msg)`。
- 发起按钮与提交按钮，成功后写 `dp_msg` → `st.rerun()`。这样 rerun 后整个页面（指标区、
  发言记录、selectbox）都基于最新数据重新渲染，绿框消息也从 `dp_msg` 带到新一帧。
- `_label()` 去掉动态数值。**selectbox 的 `format_func` 返回值会被 Streamlit 缓存**，
  label 里塞发言数/共识分永远显示首次的旧值；改成只显示「主题　[状态]」，实时数值放指标行。

修完后浏览器实测：第 1 轮 0.400 → 第 2 轮 0.457，指标区同帧同步，旧标签不再更新为
「0 条发言·共识 0.000」的死值。`Select-String "DEBUG"` 返回 `no DEBUG left`。

### 19.6 重启与刷新运维坑（本轮再次全部踩到）

- **单 pid `Stop-Process` 会漏杀。** 必须按命令行过滤全量杀：
  `Get-CimInstance Win32_Process -Filter "Name='python.exe'" | Where-Object { $_.CommandLine -like "*streamlit*" } | ForEach-Object { Stop-Process -Id $_.ProcessId -Force }`。
- **F5 / Ctrl+R / 点浏览器工具栏刷新按钮全部无效**，页面和 sid 完全不变。之前误判「`_sessions`
  被持久化」，实际是浏览器还连着旧进程。
- **有效解法四步**：全量杀 → sleep 3 → `Start-Process ... -m streamlit run dashboard.py
  --server.port 8501 --server.headless true` → sleep 12 → `Invoke-WebRequest` 验 200 →
  浏览器 `Ctrl+L` 重输 URL 回车（不是 F5）。之后 sid 才换新。
- 后台常驻 `services.long_chat`（pid 23564 / 14464）不要误杀。
- PowerShell 前台命令 15s 超时会被自动转后台，需 `TaskOutput(block=true)` 取结果；杀进程 +
  sleep + 验 200 的组合必然超时转后台，属正常。

### 20.8 本轮抓到并修掉的两个真问题

**① chromadb 多进程索引快照（真 bug，已修）**

面板检索「插件验收」只显示**命中 1 条**，而直接脚本调同一 `search_knowledge` 返回 **2 条**；
且页面条数行明确显示 `knowledge_fact：2`。定位：chromadb 多进程共用同一 persist 目录时，
每个进程的 `Collection` 对象各持一份索引快照 —— `count()` 走 sqlite 看得到新行，`query()` 却看不到别进程写入的向量。
修法：`ChromaKB.refresh_collections()`（遍历已打开集合逐个 `get_collection` 重开），
并在 `_coll_names()` 开头先调一次。重启后同一检索**命中 2 条**。

**② 「同一行显示两遍」（不是 bug，是浏览器译文扩展）**

修好索引后，结果上方出现两行几乎相同的文本：`2. id: …　distance=0.560` 与 `2. 编号：…　距离=0.560`。
一度按老经验判定为「markdown 拆行」。但 Grep 源码确认模块里**根本没有「编号」「距离」字样**，
AppTest 里 `at.markdown` 也只有一条 `'1. id: TESTID-1　distance=0.500'`（`exception count: 0`）
→ 判明是 **Edge 的浏览器译文扩展**对英文术语做双语叠加显示，同帧里能看到 `distance=0.560` 与 `距离=0.560` 并存。
仍预防性把该行从 `st.write`（走 markdown）改成 `st.text`（纯文本），源码留注释说明。

### 做了什么

**1) 工具耗时落盘（P1-4）**

`core/metrics.py` 改造，原则是「不让持久化污染测试」：

- `Metrics(persist=False)` 是默认，构造零副作用 —— `test_suite.py` 里那四个 `Metrics()` 用例完全不受影响。

- `reset()` 会覆盖写回本进程当日文件 —— 「重置」是真清空，不是只清内存，重启后不会又冒出来。

## 十五、插件安装 / 卸载（2026-11-09 中午，接第十四节）

P1-6 是清单里最后一条「要人拍板」的。用户说「按你的意思去做吧」，我按最小可用方案自己定了：
**只做本地文件夹装卸，不碰市场源、不做版本比对、不联网取包。**

理由是清单卡住的从来不是「按钮有没有」，而是「包从哪来」。市场源、依赖解析、版本兼容这些一旦碰，
就得先定义仓库协议、签名、回滚策略——那是架构级决定，不该我一个人拍。而本地文件夹装卸可以立刻解决
真实痛点：现在装一个插件要手动把文件夹拖进 `plugins/installed`，卸载要手动删目录（还得小心别删错插件）。

### 做了什么

**1) `core/plugin/registry.py` 三个方法**

- `install(src_dir, install_root, name="")`：校验 `manifest.json`（name/version/desc 三项齐全）与
  `module.py` 存在 → **目录名即插件名**（`discover()` 就是用 entry 作 key，这一点必须对齐，否则
  `_status` 查不到）→ `copytree`（忽略 `__pycache__` 与 `*.pyc`）→ `discover([install_root])` →
  状态不是 `enabled` 就如实报出来，并且**保留目录**让用户就地改 manifest。
- `uninstall(name, install_root, trash_root="")`：只认 `_FilePlugin`；用 `os.path.commonpath` 确认
  目录确实在安装根下（**不同盘符时 `commonpath` 会抛 `ValueError`，已兜住**）；移动到
  `plugins/_removed/<名>__<时间>` 而不是删除；最后 `_forget` 摘掉 `_plugins/_status/_tool_index`。
- `_forget(name)`：只清内存，不碰磁盘。

**三条边界都是故意的**：
- 不覆盖 —— 同名目录或注册表同名都直接拒绝，重装必须先卸载；
- 不删盘 —— 卸载只是移进回收区，用户随时能捞回来；
- 不越权 —— 内置插件不给卸（可停用），安装根以外的插件目录也不给卸。

**2) `dashboard.py` 页 10**

- 顶部加「📦 安装插件（从本地文件夹）」expander：源路径 + 可选改名 + 安装按钮；
- 每个 `source == "local"` 的插件多一个「卸载」按钮（按钮列从 `[1,5]` 改成 `[1,1,4]`）；
- 操作结果走 `session_state["plug_msg"]` 再 `st.rerun()` —— 同帧显示会被 rerun 冲掉，这是
  `streamlit-button-write-stale-frame` 那条经验的直接应用。

### 验证

- `_verify_plugin_io.py` **19/19 通过**，全程用独立 `PluginRegistry()` 实例 + 临时目录，
  不碰全局 registry、不碰真实 `plugins/installed`：
  - 正常安装 → 目录建了、状态 enabled、`get_tool` 能拿到、`call` 返回 `"hi !"`
  - 拒绝重复安装 / 缺 manifest / 缺 module
  - 卸载 → 目录进 `_removed`、工具从索引消失、`list_plugins` 里不再有
  - 拒绝卸载内置插件 / 拒绝卸载安装根之外的插件 / 拒绝卸载不存在的
- AppTest 页 10：`exception` 为空，`buttons` 里出现 1 个「安装」与 **10 个「卸载」**（正好对上
  `plugins/installed` 里 10 个文件插件）。
- 全量回归 **159/159 OK**（54.2s）。

### 这次自己定方案的边界

**没做的**（都在等用户拍板，不是漏做）：
- 从网络/市场拉包：需要先定源站、签名、包格式；
- 版本比对与升级：现在同名即拒绝，没有「装了 1.0 再来 1.1」的概念；
- 依赖声明与解析：manifest 里没有 `requires` 字段，插件自己 `import` 不到就是 broken。

**做这件事的判据**：改动是否会让项目进入「必须维护一个仓库协议」的状态。本地文件夹装卸不会，
所以可以自己定；市场源会，所以必须问。

## 十七、测试卫生清理：两个 ResourceWarning（2026-11-09 下午，接第十六节）

这两条警告在回归输出里飘了很久，一直没处理，理由是"不影响产品"。但回归输出被自己的噪音
污染本身就是问题——哪天真的出现一条资源泄漏，它会被埋在同一类警告里看不到。

### 警告一：图像文件句柄不关

源头是产品代码，不是测试。`test_suite.py:799` 只是**触发者**：

- `core/vision/slicer.py` 的 `slice_image()` / `crop_to_file()` 都是 `img = Image.open(...)` 之后不再关
- 同类内联写法还有 `core/vision/confidence.py:44`（`clarity_score`）、
  `core/vision/stability.py:14 / 35 / 36`（`_image_array_stats` / `frame_diff`）

改法都是同一句：`with Image.open(...) as img:`。`slice_image` 里只需要 `img.size`，
把这一行挪进 with 就够，后面的纯坐标计算不用缩进。
`frame_diff` 同时开两帧，写成 `with Image.open(a) as fa, Image.open(b) as fb:`。

### 警告二：sqlite 连接不关 —— 这里有个真陷阱

`core/desktop/queue.py` 看着很规范，每个方法都是 `with _conn() as conn:`。问题在
**`sqlite3.Connection` 作为上下文管理器时只提交/回滚事务，根本不关闭连接**。
所以每次 `enqueue` / `list_queue` / `get` / `update_status` / `auto_reject_timeout`
都漏一个 OS 句柄，测试跑一遍就是几十个。

改法：把 `_conn()` 从"返回连接"改成 `@contextlib.contextmanager`，`yield` 后 `commit`，
异常 `rollback`，`finally: conn.close()`。调用方的 `with` 写法一行不用改。
另外把 `auto_reject_timeout` 的 `n = cur.rowcount` 挪进 with 内——连接一关 cursor 就失效，
虽然当前 CPython 上还能读到 rowcount，但不能依赖这个。

顺带核了 `core/sandbox_index.py`：那里的 `get_sandbox_index_db()` 返回裸连接，但两个调用方
（`index_add_file` / `index_search`）都显式 `conn.close()` 了，不是泄漏源，按"不动没坏的东西"
原则留着没改。

### 验证

**先证明警告真的走了，再证明资源真的关了**——这两件事不一样，警告依赖 GC 时机。

1. 定向验证（`-W always::ResourceWarning`）：
   - `TestVisionSlicer` + `TestVisionStability`：4 tests OK，**零警告**（之前必报 unclosed file）
   - `TestDesktopQueue`：5 tests OK，**零警告**
2. 全量 `python -W always::ResourceWarning -m unittest test_suite`：**159/159 OK，90 秒，输出干净到没有一条 ResourceWarning**（`-W always` 会把所有警告都打出来，没打印就是没有）
3. `_verify_handles.py` **14/14**，用的是**当场就会失败**的硬证据：
   - Windows 上句柄没关时 `os.remove()` 会 `PermissionError`。所以每个函数调用后直接删源文件：
     `slice_image` / `crop_to_file`（源+输出）/ `clarity_score` / `is_black_screen` / `frame_diff`（两帧）
     全部删成功 → 句柄真的释放了
   - 连接侧用打补丁监视 `sqlite3.connect`：调用 6 个队列方法产生 6 个连接，
     逐个 `conn.execute("SELECT 1")` 全部抛 `sqlite3.ProgrammingError: Cannot operate on a closed database`
     → **closed=6 made=6**
4. `core/desktop/queue.py` 改动涉及桌面审批队列这条主链路，159 条回归里包含 `TestDesktopQueue` 的
   入队/查/改状态/超时自动拒绝/全局视图，行为未变。

### 沉淀

`sqlite3.Connection` 上下文管理器只提交不关闭这条，写进了经验库
`sqlite3-connection-context-manager-does-not-close.md`。它属于"看着用了 with 就以为安全"的
典型静默失败——和 `open()` 的直觉正好相反。


## 十八、七步第 2 步 196.4s 的真因：显存换入，不是上下文长

## 十九、常驻模型数上限：`OLLAMA_MAX_LOADED_MODELS=2`

### 用户授权

上一轮末尾我把「要不要限制常驻模型数」列成待定项，说明它会改 ollama 服务行为、影响聊天室轮转。用户回「可以」。

### 执行

1. 先确认聊天室状态：`chat.md` mtime 距当时仅 30 秒，两个 `long_chat` 进程（17912 / 28132）在跑 → 重启会打断当前一轮，但重试机制兜得住。
2. `[Environment]::SetEnvironmentVariable('OLLAMA_MAX_LOADED_MODELS','2','User')`，原值为空。
   `OLLAMA_KEEP_ALIVE` 保持为空（用 ollama 默认 5 分钟）。
3. 强杀全部 `ollama` / `llama-server` → 等 4s（确认剩 0 个）→ `Start-Process "ollama app.exe"` → 等 12s。
   新进程：`llama-server` 23908、`ollama` 7676、`ollama app` 10948。

### 验证一：上限确实生效

`_verify_vram.py` 依次唤起三个模型，每步快照 `/api/ps`：

| 动作 | 结果 | ps 快照 |
|---|---|---|
| 重启后初始 | — | 仅 `qwen3.5:4b` (3.52/3.52) |
| 唤起 `qwen3.5:4b` | 19.7s（load 17.6s，2 tok） | qwen(3.66/3.66) + llama(6.36/6.36) |
| 唤起 `llama3.1:8b` | **52.9s（load 52.7s，2 tok）** | 只剩 llama(7.26/6.5)，qwen 被驱逐 |
| 唤起 `deepseekR1Q7B` | 9.5s（load 8.6s，4 tok） | deepseek(5.64/5.64) + llama(7.26/6.5) |

→ ps 任何时刻最多 2 个，第三个进来时最旧的被踢。**上限生效。**

同时看到代价：`llama3.1:8b` 被驱逐后重载要 52.7s，且 `size_vram 6.5 / size 7.26`——12288 窗口下仍装不满。

### 验证二：`num_ctx` 才是显存的直接杠杆

`_verify_ctx.py`（8192 窗口，模拟七步第 2 步的 prompt 规模，两连跑）：

| run | 耗时 | load | 输出 | ps |
|---|---|---|---|---|
| #1 | 70.2s | 37.4s | 465 chars JSON | 只剩 deepseek |
| #2 | 31.2s | 28.4s | 223 chars JSON | **llama(5.82/5.82)** + deepseek(5.64/5.64) |

→ **决定性**：8192 下 8b 只要 **5.82GB，`size == size_vram`**，100% 进显存；12288 时是 7.26/6.5。
那 1.4GB 差就是 KV cache。

两条配置互补：`max_loaded_models=2` 管**次数**（别让三个挤），`num_ctx=8192` 管**单次量**（让一个装得下）。

### 剩下的账

8b(5.82) + deepseek(5.64) = **11.46GB**，8GB 单卡装不下，两个大模型共存照样换入。
想要零换入，只能让一条流程只用一个模型——七步已经统一走 light，正是这个思路。

聊天室三个角色轮转是产品设计（用户明确圈定不动），所以它会一直换入。这是硬件边界，不是代码问题。

经验条目 `ollama-api-ps-listed-but-half-on-cpu.md` 补了「实测数据（2026-11-09，加 max_loaded_models 之后）」一节：

### 方法论

**硬件瓶颈要拆成「次数」和「单次量」两个维度。** 只限驻留个数，能减少换入次数，但单次换入还是要 52.7s；
只降 num_ctx，单次能装下，但三个一起挤还是会被踢。这两件事必须分开做、分别验证。
